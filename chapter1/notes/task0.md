# Agent 理解

## 核心公式

**Agent = LLM + 上下文 + 工具**

## ReAct：上下文驱动的"想→看→做"

把轨迹串起来：**prompt + tools + 用户信息 + 模型回答 + 工具执行结果**，每一步都把上一轮的反馈塞回上下文，循环推进。

```
prompt + tools + 用户信息 ─┐
       ↓                    │
  模型回答（想）             │  ←── 累积成上下文
       ↓                    │
工具执行结果（看→做） ──────┘
```

## 第一章实验

- **1-1 context**：上下文消融，验证各组件的真实影响
- **1-2 web-search-agent**：Kimi K3 等"模型即 Agent"，自带基础工具与多轮搜索
- **1-3 search-codegen**：厂商 Deep Research 闭环（hosted web_search + code_interpreter）——自主多轮搜索 + 服务端代码执行
- **1-4 image-gen-workflow**：工作流（kimi-k3 改写 + 通义万相）vs 原生（Gemini / GPT-Image 2）双路线对比

## 关键问题

### 1. 上下文各组成的作用？

| 组件 | 作用 |
|---|---|
| prompt | 定义 Agent 身份、能力边界、行为约束 |
| tools | 告诉模型能调什么、参数是什么，扩展能力 |
| 用户信息/历史 | 多轮连贯性与个性化 |
| 模型回答 | 当前轮的思考与决策（ReAct 的"想"） |
| 工具执行结果 | 让模型"看到"真实世界的反馈（ReAct 的"看→做"） |

1-1 实验通过逐项消融验证每一项的必要性。

### 2. 模型客户端 = Agent 吗？

**不是**。

- 客户端只是 LLM 的 API 包装（文本 → 文本），无工具调用、无轨迹维护、无循环决策
- 即使 Kimi K3 这种"模型即 Agent"，背后仍是厂商把 **harness 内化进了模型服务层** —— 模型本身仍是 LLM，闭环仍由 harness 编排

### 3. 业务闭环还需自建吗？

**是的**。厂商 API 提供的是通用能力，业务闭环仍需自建：

- 业务专属工具（内部 API、数据查询）
- 上下文注入（私有数据、prompt 工程）
- 异常处理与 fallback（1-3 实验中 GPT-5.6 配额阻塞就是典型场景）
- 结果验证与人机协作

**厂商 API 是"能力"，不是"成品"。**

### 4. 模型之外，harness 的作用？

把模型接入真实世界并稳定运行所需的一切工程：

- **上下文管理**：trajectory 维护、history 截断、token 预算
- **工具调度**：schema 校验、结果解析、异常处理
- **错误恢复**：fallback、超时、重试、限流
- **可观测性**：日志、trace、指标
- **安全护栏**：注入防护、权限控制
- **评测与自我改进**：7-1、7-2 Q-learning 实验正是 harness 通过反馈自我进化
